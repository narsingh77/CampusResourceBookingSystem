1. Introduction

In our college campus at VIT Bhopal, university infrastructure—ranging from the Sir Visvesvaraya Auditorium and high-performance computing labs to departmental conference rooms—is heavily utilized every week. Managing these resources across faculty lectures, guest seminars, and student club activities (like technical workshops and hackathons) is often challenging when done through manual permission slips, emails, or spreadsheets.

To address this practical campus issue, I designed and developed CampusResourceHub, a standalone Java console application. The project translates core concepts learned in the Programming in Java curriculum into a practical system. It leverages Object-Oriented Programming (inheritance hierarchies, polymorphism, interfaces), the Java Collections Framework, multi-threaded synchronization for conflict resolution, custom exception handling, Java 8+ Streams API for analytics, and file persistence.

2. Problem Statement

During college events, resource allocation typically encounters four main bottlenecks:

  • Simultaneous Booking Clashes: Two organizers or faculty members might request the same venue for overlapping hours, resulting in double-bookings.
  • Priority Ambiguity: High-priority university-level academic events or exams need a mechanism to take precedence over informal student club practice sessions.
  • Unmonitored Booking Quotas: Without systemic constraints, a single student organization can reserve multiple venues simultaneously, depriving other clubs of available slots.
  • Lack of Real-Time Utilization Metrics: Campus administration lacks visibility into which facilities have the highest demand and total hours used.

3. Functional Requirements

The system is organized into three major functional modules:

3.1 Module 1: User Roles & Quota Management

  • Role-Based Access: Implements an abstract base User class with three concrete subclasses: AdminUser, FacultyUser, and StudentClubUser.
  • Dynamic Quota Constraints: Enforces systemic booking limits based on role (e.g., max 3 active concurrent bookings for student clubs, 10 for faculty, unlimited for administrators).
  • Role Switching: Allows switching active users at runtime to demonstrate access restrictions and permission enforcement.

3.2 Module 2: Resource Catalog & Thread-Safe Reservation Engine

  • Specialized Venue Modeling: Models venues using an abstract CampusResource class extended by Auditorium, ComputerLab (tracking GPU workstations and OS), and ConferenceRoom (tracking smartboards and AV setups).
  • Time-Window Overlap Detection: Implements a TimeSlot value object utilizing java.time.LocalDateTime to calculate temporal overlap with mathematical precision.
  • Thread-Safe Concurrency Locks: Protects venue allocations using intrinsic monitor locks mapped per resource (ConcurrentHashMap<String, Object>) to eliminate race conditions.
  • Priority-Based Preemption: When a faculty member books a slot already occupied by a student club, the system cancels the club booking with an audit note and assigns the slot to faculty.

3.3 Module 3: Streams Analytics, Audit Trail & CSV Export

  • Java Streams Analytics: Computes real-time facility utilization using declarative stream operations (filter, map, groupingBy, summingDouble).
  • Audit Trail Ledger: Records every booking, cancellation, and preemption action into a thread-safe log with timestamps.
  • CSV Report Export: Exports historical reservation data into a standardized CSV file.

4. Non-Functional Requirements

  • Performance: Fast slot search and clash validation (<10 ms) utilizing in-memory hash maps and localized locking.
  • Reliability & Concurrency Safety: Guaranteed prevention of double-bookings even under simultaneous multi-threaded requests, validated using automated CountDownLatch stress testing.
  • Maintainability: Clean modular design across 14 decoupled Java classes, interfaces, and custom exception types.
  • Explicit Exception Handling: Domain-specific checked exceptions (SlotConflictException, QuotaExceededException, ResourceNotFoundException, UnauthorizedAccessException).
  • Ease of Execution: Self-contained CLI runnable with standard javac and java without external build tools or databases.

5. System Architecture

The application uses a 4-tier layered architecture separating presentation, business logic, domain entities, and data persistence:

  • Presentation Layer: CLI console menu (Main.java) and automated test runner (TestRunner.java).
  • Service Layer: Business logic coordination (BookingService, UserService, ResourceService, AnalyticsService).
  • Domain Model Layer: OOP entities (User hierarchy, CampusResource hierarchy, Reservation, TimeSlot).
  • Persistence Layer: File I/O serialization (StorageManager) and CSV generation.

8. Implementation Details

The project consists of 14 well-structured classes under com.vityarthi.booking:

  • model/UserRole.java: Enum specifying priority levels and max quotas.
  • model/User.java: Abstract class holding identity fields.
  • model/AdminUser.java, FacultyUser.java, StudentClubUser.java: Concrete user implementations.
  • model/CampusResource.java: Abstract resource base with abstract methods getResourceType() and getHourlyCostRate().
  • model/Auditorium.java, ComputerLab.java, ConferenceRoom.java: Concrete venue models.
  • model/TimeSlot.java: Value object with overlap logic:
    public boolean overlapsWith(TimeSlot other) {
      return this.startTime.isBefore(other.endTime) && this.endTime.isAfter(other.startTime);
    }
  • model/Reservation.java: Immutable record tracking status and audit remarks.
  • service/BookingService.java: Thread-safe reservation engine with preemption.
  • service/AnalyticsService.java: Streams aggregator and CSV exporter.
  • util/StorageManager.java: Java Object Serialization persistence.
  • Main.java: Interactive 10-option command-line console.

11. Challenges Faced & Practical Solutions

During the development of this project, I ran into several issues that took time and experimentation to resolve:

  1. Dealing with Race Conditions in Concurrent Requests:
    When I first tested my booking logic with two threads, both of them managed to book the same auditorium slot. It took me a while to understand why—both threads were reading the slot as available before either of them could write their reservation. I spent time reading about Java concurrency primitives and eventually learned about lock striping. Instead of locking the entire system with one giant synchronized block (which would have been slow), I created a separate lock object for each resource ID using ConcurrentHashMap.computeIfAbsent(). This way, if two clubs are booking different rooms, they don’t block each other at all—only threads going after the exact same venue need to wait.
  2. Getting Priority Preemption Right Without Corrupting State:
    I wanted faculty bookings to override student club ones when there’s a clash. But in my first attempt, I was cancelling the old booking and creating the new one in separate steps, which briefly left the slot in a weird state. To fix this, I moved both operations—cancelling the club reservation and creating the faculty one—inside the same synchronized block. This way, the slot never appears “empty” between the cancel and the new booking.
  3. Making It Work on Any Computer Without Setup Hassle:
    In a previous project I tried using MySQL, and the evaluator couldn’t run it because they didn’t have the database installed. This time I deliberately avoided external dependencies. Everything runs with just javac and java. For persistence, I used Java’s built-in Object Serialization. For testing, instead of pulling in JUnit via Maven, I wrote a simple custom test runner with assertion checks.

12. Learnings & Key Takeaways

Working on this project gave me a much deeper understanding of Java than I had from just studying lecture slides. Here are the main things I took away:

  • OOP Actually Makes Sense in Practice: Before this project, abstract classes and interfaces felt like unnecessary complexity. But when I needed to add a new venue type (ConferenceRoom), I just extended CampusResource and implemented two methods. Everything else—booking, analytics, display—worked automatically because of polymorphism. That was a real “aha” moment for me.
  • Concurrency Is Harder Than It Looks: I thought adding synchronized to a method would be enough. It wasn’t. I learned about lock granularity, the importance of CountDownLatch for firing threads simultaneously in tests, and why ConcurrentHashMap is preferred over wrapping a regular HashMap with synchronized blocks.
  • Streams API Changed How I Think About Data: Computing analytics using filter().collect(groupingBy()) was so much cleaner than the nested for-loops I was writing before. It also helped me appreciate lambda expressions and method references.
  • Good Exception Design Saves Debugging Time: Instead of printing generic error messages, having named exceptions like QuotaExceededException made it immediately clear what went wrong during testing. I didn’t have to add print statements everywhere to trace bugs.
